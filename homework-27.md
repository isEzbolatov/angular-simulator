# Homework 27 — Dependency Injection

## Задача №1. Singleton или нет?

`CounterService` зарегистрирован через `providedIn: 'root'`, поэтому Angular создаёт один экземпляр в корневом инжекторе. Все компоненты получают ссылку на этот общий экземпляр. Сервис является singleton.

## Задача №2. Локальный Provider

Если сервис указан в `providers` компонента, создаётся локальный экземпляр для этого компонента и его дочернего дерева. Компоненты вне этой ветки его не видят и используют другой доступный провайдер либо получают ошибку.

## Задача №3. Какой экземпляр получит компонент?

Если сервис зарегистрирован и в `root`, и локально у компонента, Angular выберет локальный экземпляр. Поиск зависимости идёт снизу вверх, поэтому ближайший провайдер имеет приоритет.

## Задача №4. `useExisting`

`useExisting` не создаёт новый объект. Второй токен получает ссылку на уже существующий экземпляр сервиса, поэтому оба токена обращаются к одному объекту и видят одинаковое состояние.

## Задача №5. `useFactory`

`useFactory` получает значение от фабричной функции. Фабрика вызывается при первом запросе зависимости, после чего значение используется повторно в рамках соответствующего инжектора.

## Задача №6. Multi Provider

При `multi: true` несколько провайдеров регистрируются под одним токеном. При внедрении Angular возвращает массив всех зарегистрированных значений.

## Задача №7. `Optional`

`@Optional()` делает зависимость необязательной. Если провайдер не найден, Angular передаёт `null`, а не выбрасывает ошибку.

## Задача №8. `Self`

`@Self()` ограничивает поиск текущим инжектором компонента. Angular не поднимается к родителям, поэтому при отсутствии локального провайдера возникнет ошибка.

## Задача №9. `SkipSelf`

`@SkipSelf()` пропускает текущий инжектор и начинает поиск у родителя. Если провайдер есть и локально, и у родителя, будет выбран родительский экземпляр.

## Задача №10. Нет регистрации

Если сервис нигде не зарегистрирован и у него нет `providedIn`, Angular не знает, как его создать. При внедрении возникнет `NullInjectorError`.

## Задача №11. Два `inject()` одного сервиса

`LoggerService` зарегистрирован через `providedIn: 'root'`. Два вызова `inject(LoggerService)` получают один и тот же singleton-экземпляр из корневого инжектора, поэтому `logger1 === logger2` равно `true`.

## Задача №12. Финальная иерархия

Существует два экземпляра `LoggerService`: корневой и локальный у `HeaderComponent`.

- `HeaderComponent` получает локальный экземпляр.
- `DashboardComponent` получает корневой экземпляр, потому что локальный провайдер соседнего компонента ему недоступен.
- `UserCardComponent` также получает корневой экземпляр.
- Поиск для `UserCardComponent` идёт так: `UserCardComponent → DashboardComponent → AppComponent → root`.

## Задача №13. Цепочка зависимостей

При `inject(A)` Angular находит провайдер `A` и начинает его создание. Затем видит зависимость `B`, в `B` находит `C`, в `C` — `D`, а в `D` — `LoggerService`.

Сначала создаётся нижняя зависимость `LoggerService`, затем Angular возвращается вверх по цепочке и создаёт `D`, `C`, `B` и `A`. Цепочка выглядит так: `A → B → C → D → LoggerService`.

## Задача №14. Ленивое создание

До первого `inject(UserService)` экземпляры сервисов не созданы: `providedIn: 'root'` только регистрирует правило их создания.

После `inject(UserService)` Angular создаёт три объекта по цепочке зависимостей: `LoggerService`, затем `ApiService`, затем `UserService`. Сервисы создаются лениво, только когда реально запрашиваются.

## Задача №15. Архитектура интернет-магазина

1. `ApiService` — `providedIn: 'root'`, потому что HTTP-доступ общий для всего приложения.
2. `AuthService` — `providedIn: 'root'`, чтобы состояние авторизации было единым на всех страницах.
3. `CartService` — `providedIn: 'root'`, чтобы корзина сохранялась при переходах между страницами.
4. `ProductFilterService` — локальный `providers` страницы, чтобы фильтры телефонов и ноутбуков были независимыми и сбрасывались после ухода.
5. `NotificationService` — `providedIn: 'root'`, потому что toast-уведомления нужны любому компоненту.
6. `ThemeService` — `providedIn: 'root'`, чтобы все страницы использовали одну тему.
7. `DashboardStatisticsService` — локальный `providers` у `DashboardComponent`, потому что статистика нужна только Dashboard.
8. `UserTableStateService` — локальный `providers` у `UsersPage`, потому что сортировка, страница и фильтры относятся только к пользователям.
9. `ModalService` — `providedIn: 'root'`, чтобы любой компонент мог открыть общее модальное окно.
10. `LoggerService` — `useFactory`, потому что фабрика выбирает реализацию для production или development.
11. `AppConfig` — `InjectionToken` с `useValue`, потому что передаётся готовый объект конфигурации.
12. `CurrencyFormatter` — `InjectionToken` с `useValue`, потому что через DI передаётся готовый формат числа.
13. `AnalyticsService` — `useFactory`, потому что сервис должен создаваться только при включённой аналитике.
